# Node memory metrics

Node memory pressure is sampled from `/proc/meminfo` as visible to sandboxd. In the bundled privileged node deployment this is host memory, not the node container's cgroup limit. This works on cgroup v1 and v2, including the unified hierarchy root where `memory.current` does not exist. A deployment that virtualizes `/proc/meminfo` must account for that scope when interpreting these metrics.

`node.memory.usage` reports `MemTotal - MemAvailable` in bytes. Unlike raw cgroup charges, it excludes memory the kernel estimates can be reclaimed without swapping. `node.memory.physical.total` reports `MemTotal`, and `node.memory.available` reports `MemAvailable`. `node.memory.utilization` reports `(MemTotal - MemAvailable) / MemTotal` as a ratio in `[0, 1]`. These four metrics share one snapshot; missing or invalid input omits the host memory samples and logs the read failure. Other metrics continue to export.

`node.memory.total` retains its existing meaning: schedulable capacity from the resource manager, also served over the resource socket. It is not the denominator for physical memory utilization. Use `node.memory.utilization`, or divide `node.memory.usage` by `node.memory.physical.total`, for a host-pressure dashboard. Scheduling allocation and per-sandbox cgroup usage/limits are unchanged. Host pressure and reserved sandbox memory answer different questions and must not be substituted for each other.

With the usual Prometheus name translation, these are `node_memory_usage_bytes`, `node_memory_physical_total_bytes`, `node_memory_available_bytes`, `node_memory_utilization_ratio`, and the existing `node_memory_total_bytes`. Consumers must explicitly adopt the host utilization metric; changing sandboxd does not by itself add memory-based decisions to an external scaling controller.

## Resource reporting and freshness

The `/resource` socket retains the scheduler capacity contract: `cpu` is in cores and `mem` is in bytes, computed from the configured provider and existing transient reservations. Running sandbox usage is reported separately as `sandbox_mem_usage`, including the managed sandbox subtree and the Firecracker checkpoint sibling when present. A checkpoint group within the managed subtree is already included in the rollup. A checkpoint group that contains the managed root makes the combined observation unavailable because its aggregate overlaps the root. It is not subtracted from `mem`: schedulers that already reserve instance requests would otherwise count those instances twice. This observation does not by itself implement an admission or overcommit policy.

The Kubernetes provider requires complete node and pod snapshots and live watches for both. A quiet watch remains valid without recent events. A disconnected, errored, or unestablished watch makes provider refreshes fail; repeated reads of its old cache do not renew freshness. Each reconnection starts from a successful complete list and its resource version, so failed initial lists and expired watch histories cannot silently leave pod requests missing. List requests have a 10-second deadline and watch requests have a one-minute lifetime, bounding a stalled request or undetected broken stream before retrying. Failed lists and repeated short-lived watches increase the retry delay from one second to at most one minute. A watch that lasts at least 30 seconds resets the delay.

The resource module keeps the last capacity during its 30-second grace period after the last successful provider refresh. After that window, including when the capacity refresh is blocked, health fails and `/resource` returns HTTP 200 with explicit `cpu: 0` and `mem: 0`, allowing consumers that cache successful responses to observe the loss of capacity. A complete snapshot followed by both live watches restores fresh capacity on the next refresh.

Sandbox usage is sampled independently of capacity. A read failure or timeout logs a warning, and `sandbox_mem_usage` is omitted 30 seconds after the last successful sample. A read that takes 30 seconds or longer is discarded. The sampler allows one read at a time and resumes after the outstanding read returns. Capacity can keep refreshing during that time, and shutdown can finish while the outstanding read drains.

On cgroup v2, the hierarchy root `/` supplies node CPU accounting without requiring memory controller files, which Linux does not expose there. Memory reads for the managed sandbox root, sandbox children, and checkpoint sibling remain strict: an unreadable or invalid `memory.current` is an error rather than fabricated zero usage. Host memory pressure continues to use `/proc/meminfo`.

On cgroup v1, sandboxd creates the managed memory root before filling the cgroup pool and enables `memory.use_hierarchy=1` while the root has no children. Aggregate sampling checks that setting on every read and requires a valid `memory.usage_in_bytes`; disabled, missing, or invalid accounting is unavailable data, never zero usage. Already hierarchical trees need no control-file write. Existing non-hierarchical trees are preserved for sandbox recovery because the kernel cannot enable hierarchy while child cgroups exist. In that case startup warns and aggregate samples fail. The module omits `sandbox_mem_usage` until the first successful sample. Individual sandbox accounting and the `mem` capacity contract retain their existing semantics.

To recover an existing non-hierarchical tree, stop new work and drain sandboxes through the normal workload lifecycle. Stop sandboxd to halt pool replenishment, verify that no live processes remain in the managed subtree, and remove its remaining idle child cgroups. Enable and verify `memory.use_hierarchy=1` on the empty managed memory root before restarting sandboxd. Do not delete populated cgroups or migrate live processes merely to obtain an aggregate observation. Permission or control-file errors require fixing the memory-controller delegation before recovery.

The optional `online_cgroup` provider requires the configured cgroup v1 layout and an Alibaba Cloud NodeResource response containing explicit CPU and memory quantities. Every refresh checks the cloud ceiling and the relevant controller files. CPU headroom is zero on the first complete sample and when any CPU accounting counter resets. The first measured interval after either event reports its calculated headroom and initializes smoothing for later intervals. Measured memory capacity remains available while the CPU baseline is established. Once a smoothed increase is within one millicore or one MiB of the measured CPU or memory headroom, respectively, the provider reports the measured value so rounding does not prevent exact whole-unit recovery. If a listed pod disappears during the refresh, sampling continues with the remaining pods. A failed or incomplete sample for an existing pod follows the same grace period as other providers. An explicit zero cloud ceiling is a zero budget.
